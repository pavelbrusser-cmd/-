# Размещение сервера действий

Для самостоятельного прохождения экранов Render используйте
[пошаговую инструкцию](render-walkthrough.md). Она включает подготовку GitHub,
ввод доступов и оплату во внешнем окне браузера, а также проверку запуска.

Рекомендуемый вариант — платный веб-сервис Render с постоянным диском.
Он даёт публичный HTTPS-адрес и работает без засыпания при отсутствии запросов.
Сервер нужен для перехода из письма к подтверждению, отмене и переносу событий.
Сервис уже размещён на Render, чтение всех четырёх аккаунтов проверено.
После исправления потребления памяти полный сбор на 15 октября 2026 года
вернул 35 событий из 11 календарей. Пользователь проверил перенос личного
тестового события первого аккаунта Mail.ru с 15:00 на 16:00.
После следующего обновления пользователь проверил отмену этого личного события:
оно удалено из Mail.ru и осталось в истории дайджеста без кнопок. Также проверено
принятие приглашения вторым аккаунтом Mail.ru с отображением ответа организатору
в первом аккаунте. Остальные сочетания действий и провайдеров этим не проверены.
Правила отмены описаны в [cancellation.md](cancellation.md).

## Подготовленная конфигурация

Один экземпляр Python 3.12.14 во Франкфурте, план `0.5c-512mb`
(0,5 CPU, 512 MB RAM), постоянный диск 1 GB в `/var/data`.
Сервер Gunicorn использует один процесс, четыре потока и тайм-аут 90 секунд.
Новая команда запуска `.venv/bin/python scripts/start_service.py` управляет
веб-сервером и отдельным процессом планировщика в том же контейнере.
Расписание включается только через `DIGEST_SCHEDULE_ENABLED=true` после
проверки письма и итогового подтверждения владельца; по умолчанию оно выключено.
Журнал запросов Gunicorn отключён, чтобы ссылки с токенами не попадали в него.
Render проверяет доступность процесса через `/health`; это не проверка прав
изменения календарей или доставки приглашений.

Диск хранит SQLite с состояниями действий и другие постоянные данные приложения.
Функция отмены использует эту же `actions.sqlite3` для приватных резервных
копий и подтверждённых отмен; новый сбор дайджеста архив не очищает.
Новая отправка использует отдельную `deliveries.sqlite3` на этом же диске.
Без него обычная файловая система Render теряет изменения при перезапуске
или новом развёртывании. Диск доступен одному экземпляру и только во время
работы сервиса, поэтому он не используется при сборке. Стоимость сервиса
и диска Render покажет до создания; бесплатный экземпляр для этой конфигурации
не подходит. При обновлении сервиса с диском возможен короткий перерыв работы.

## Порядок первого запуска

Эти шаги уже пройдены для текущего сервиса и сохраняются для повторного
размещения. Обновление выполняется в существующем сервисе через
**Manual Deploy → Deploy latest commit** после объединения изменений с `main`.
Для перехода на версию с отправкой сначала явно замените **Start Command**
в настройках сервиса на `.venv/bin/python scripts/start_service.py` и оставьте
`DIGEST_SCHEDULE_ENABLED=false`. Ручной деплой сам по себе не гарантирует
применения изменённой команды из Blueprint.

1. Сначала сохранить исходники, зависимости и `render.yaml` в ветке `main`
   репозитория GitHub. Наличие файлов только в текущей облачной сессии
   не позволяет Render получить проект.
2. В Render создать учётную запись, подключить этот репозиторий через GitHub
   и выбрать **New → Blueprint**. Render прочитает `render.yaml`.
3. В защищённых настройках Render задать восемь переменных календарей:
   `ICLOUD_USERNAME`, `ICLOUD_APP_PASSWORD`, `MAILRU_1_USERNAME`,
   `MAILRU_1_APP_PASSWORD`, `MAILRU_2_USERNAME`, `MAILRU_2_APP_PASSWORD`,
   `MAILRU_3_USERNAME`, `MAILRU_3_APP_PASSWORD`. Учётные данные текущей среды
   автоматически в Render не переносятся. Значения вводятся в интерфейсе
   хостинга, без отправки в чат и сохранения в репозиторий.
4. Проверить выбранный платный сервис и диск, затем запустить Blueprint.
   Команда сборки `bash scripts/setup.sh` устанавливает зависимости и выполняет
   автоматические проверки. Календарные события при сборке не изменяются.
5. После успешного развёртывания открыть HTTPS-адрес сервиса. Приложение берёт
   его из стандартной переменной `RENDER_EXTERNAL_URL`; вручную прописывать
   новый адрес в коде не требуется. Главная страница показывает готовность
   сервиса, а вход открывается по кнопке из дайджеста. Для входа используется сгенерированный
   `DIGEST_WEB_PASSWORD`, доступный владельцу в настройках сервиса.
   В Shell этого же сервиса выполнить `.venv/bin/calendar-digest preview`,
   затем `.venv/bin/calendar-digest issue-actions --date YYYY-MM-DD` с датой
   подготовленного дайджеста. Файлы и SQLite сохранятся в `/var/data`.
   Полученный `email-actions-YYYY-MM-DD.html` содержит рабочие ссылки;
   почтовая отправка пока выполняться не будет.
6. Проверить вход и работу действий на отдельном тестовом событии, включая
   повторное чтение результата из календаря. Только эта проверка подтверждает
   изменение у конкретного провайдера.

Render создаёт `DIGEST_ACTION_SECRET` и `DIGEST_WEB_PASSWORD` автоматически
через `generateValue: true`. Ключ подписи нужно сохранять между развёртываниями:
его замена делает ранее выданные ссылки недействительными. Переменные
с `sync: false` запрашиваются при первом создании Blueprint; последующие
изменения секретов выполняются в защищённых настройках сервиса.

Автоматическое развёртывание каждого коммита отключено. После обновления кода
можно запустить новое развёртывание выбранной версии из панели Render.
Нельзя подключить тот же локальный диск к отдельному cron-сервису.
SMTP-отправка и планировщик запускаются в том же сервисе. Подготовка начинается
в 16:40 по Москве, передача письма — в 17:00. При новом размещении расписание
по умолчанию выключено.
Обновление, ввод SMTP-доступов и поэтапная проверка описаны в
[email-delivery.md](email-delivery.md).

Конфигурация сверена с официальной документацией Render:
[Blueprint specification](https://render.com/docs/blueprint-spec),
[Persistent disks](https://render.com/docs/disks),
[Python version](https://render.com/docs/python-version).
