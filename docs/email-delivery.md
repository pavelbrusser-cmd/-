# Ежедневная отправка дайджеста

Отправитель — отдельный ящик Яндекс Почты, получатель — согласованный адрес.
Адреса и пароль приложения вводятся владельцем в **Environment** существующего
сервиса Render во внешнем окне браузера. Их не нужно присылать в чат или
сохранять в репозитории.

Расписание начинает сбор дайджеста следующего дня в **16:55 по Москве**
(`Europe/Moscow`), затем передаёт готовое письмо почтовому серверу
в **17:00**. Если сбор задержался, отправка возможна после его завершения
в пределах окна до 17:30.
Точное время получения зависит также от почтовых служб.
При новом размещении автоматическая отправка выключена до итогового
подтверждения владельца.

На действующем сервисе версия развёрнута, авторизация Яндекса и настоящее
проверочное письмо проверены. Владелец подтвердил получение, оформление
и работу кнопок. Ежедневное расписание одобрено и включено 15 октября
2026 года; проверена свежая отметка работы планировщика. Получение первой
отправки по расписанию ещё не подтверждено. Шаги ниже остаются инструкцией
для нового подключения: при обычном обновлении уже настроенного сервиса
повторно выключать расписание не требуется.

## Сначала обновить сервис

Проходите по одному шагу и проверяйте результат перед следующим.

1. Объединить pull request ежедневной отправки с `main` в GitHub.
2. В существующем сервисе Render открыть **Settings → Build & Deploy** и
   явно задать **Start Command**:

   ```text
   .venv/bin/python scripts/start_service.py
   ```

   Эта команда запускает веб-сервис и, когда разрешено, планировщик.
   Обычный **Manual Deploy** обновляет код, но не гарантирует применение
   изменённого `startCommand` из Blueprint. Старая команда прямого запуска
   Gunicorn не запускает планировщик.
3. В **Environment** оставить `DIGEST_SCHEDULE_ENABLED=false`, сохранить
   настройки и выполнить **Manual Deploy → Deploy latest commit**.
4. Дождаться **Live** и проверить `/health`. В журнале запуска должна быть
   строка «Расписание выключено». SMTP-доступы при выключенном расписании
   для запуска веб-сервиса не требуются.

## Подготовить Яндекс Почту

1. Войти в ящик отправителя в своём браузере и открыть
   [Почтовые программы](https://mail.yandex.ru/#setup/client).
2. Включить **С сервера imap.yandex.ru по протоколу IMAP** и
   **Пароли приложений и OAuth-токены**, затем сохранить изменения.
   Яндекс требует эти настройки и для программы, которая только отправляет
   письма по SMTP. Приложение дайджеста входящую почту не читает.
3. Открыть [Пароли приложений](https://passport.yandex.ru/security/app-passwords)
   в Яндекс ID и создать отдельный пароль типа **Почта**, например с названием
   «Дайджест календарей». Пароль показывается один раз; сохранить его в
   защищённых настройках Render.

В официальной справке Яндекс ID указано, что новый пароль приложения начинает
действовать через **2–3 часа**. Если сразу после создания авторизация не проходит,
это нужно учесть перед заменой пароля. Обычный пароль входа в Яндекс ID для
этой настройки не используется.

## Настроить существующий сервис Render

Добавить переменные через панель сервиса, не через командную строку Shell:

| Переменная | Значение |
| --- | --- |
| `SMTP_HOST` | `smtp.yandex.ru` |
| `SMTP_PORT` | `465` |
| `SMTP_SECURITY` | `ssl` — TLS с начала соединения |
| `SMTP_USERNAME` | Адрес ящика отправителя |
| `SMTP_PASSWORD` | Отдельный пароль приложения типа «Почта» |
| `DIGEST_SENDER_NAME` | Необязательное имя отправителя для отображения в письме |
| `DIGEST_RECIPIENT` | Согласованный адрес получателя |
| `DIGEST_SCHEDULE_ENABLED` | `false` до итогового подтверждения |

Существующие настройки календарей, ключи действий и `DIGEST_STATE_DIR=/var/data`
сохраняются. Пароль для SMTP относится к ящику Яндекса; доступы четырёх
календарных аккаунтов его не заменяют.

На бесплатных веб-сервисах Render исходящие соединения на порты **25, 465 и 587**
заблокированы. Текущий платный план `0.5c-512mb` не относится к этому ограничению.
Реальное соединение с Яндексом и авторизация проверяются отдельно перед
отправкой: наличие платного плана само по себе не подтверждает доставку письма.

## Размещение планировщика

Планировщик запускается отдельным процессом в том же контейнере, что и сервер действий.
Это позволяет использовать существующий постоянный диск `/var/data` и обходится
без дополнительного платного сервиса. Render разрешает подключать такой диск
только к одному экземпляру одного сервиса, только во время его работы.
Отдельный Render Cron Job не может подключить этот диск; диск также недоступен
при сборке, в pre-deploy command и one-off job.

Сервис остаётся в одном экземпляре. Состояние отправок хранится в
`/var/data/deliveries.sqlite3`, а подготовленные письма — рядом на приватном
диске. После подтверждённого приёма SMTP-сервером повторный запуск не отправляет
второе письмо той же категории за ту же дату дайджеста. Проверочная и ежедневная
отправки учитываются отдельно.

До **17:30 по Москве** выполняются повторные попытки только для ошибок,
при которых достоверно известно, что сервер не принял письмо. Если результат
передачи неизвестен, автоматический повтор может создать дубликат и не выполняется.
После перезапуска планировщик работает только с дайджестом следующего дня:
пропущенные письма за прошлые дни автоматически не отправляются.

Чтобы сбор не конкурировал за память с изменением события, календарные формы
на время сбора могут ответить **503 «Календари временно заняты»**. Нужно немного
подождать и повторить попытку. Ссылка действия при этом остаётся доступной.

## Проверка и включение

Выполнять в Shell того же сервиса, после обновления кода и сохранения SMTP-настроек:

1. Проверить TLS-соединение и авторизацию SMTP без отправки письма:

   ```bash
   .venv/bin/calendar-digest probe-smtp
   ```

2. Только после явного разрешения отправить проверочное письмо выполнить
   `send-test` с выбранной датой. Команда соберёт
   свежие события, создаст рабочие ссылки и **отправит настоящее письмо**:

   ```bash
   .venv/bin/calendar-digest send-test --date YYYY-MM-DD
   ```

   Без `--date` используется завтра по Москве. Проверочное письмо за одну
   дату отправляется один раз: повторный запуск после состояния `accepted`
   возвращает прежний результат, а после `uncertain` не повторяет передачу.

3. Проверить внешний вид, получение и переход по ссылке из почтового клиента.
   Состояние доставки можно проверить без вывода адресов и содержания:

   ```bash
   .venv/bin/calendar-digest delivery-status
   ```

4. После итогового подтверждения владельца включить
   `DIGEST_SCHEDULE_ENABLED=true` в Render и применить изменения с перезапуском.
   После **Live** снова выполнить `delivery-status` и проверить
   `schedule.enabled=true`, `schedule.heartbeat_recent=true` и свежий
   `schedule.heartbeat_at`. `schedule.activity` показывает ожидание (`idle`),
   подготовку (`preparing`) или отправку (`sending`). Одного значения переменной
   или успешного `/health` недостаточно для подтверждения запуска расписания.

Для состояния используется `DIGEST_STATE_DIR` (в Render — `/var/data`);
при необходимости каталог можно
явно задать через `--directory` у `send-test` и `delivery-status`.
Команды `prepare-delivery` и `send-ready` разделяют подготовку и отправку
для планировщика; для обычной проверки используется `send-test`.
Если подготовка или отправка уже выполняется, `delivery-status` может вернуть
`busy=true` и пустой `deliveries`; это не означает отсутствия истории.
Отметка `schedule` при этом остаётся доступна.

`accepted` означает, что SMTP-сервер принял письмо. Это ещё не подтверждение
появления письма во входящих: получение, папку «Спам» и работу ссылок проверяет
владелец в своём почтовом клиенте. `uncertain` означает неизвестный результат
передачи; сначала нужно проверить почтовый ящик, а не повторять отправку.

Для локальной проверки запуска без отправки писем и изменения календарей:

```bash
.venv/bin/python scripts/check_action_service.py --runtime
```
