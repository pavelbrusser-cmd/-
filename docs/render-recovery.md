# Если Render перезапустил сервис из-за памяти

Сообщение Render о превышении памяти относится к лимиту экземпляра сервиса.
Открытый Shell и запущенный в нём `preview` также используют ресурсы экземпляра.
Успешный `/health` после перезапуска подтверждает восстановление веб-процесса,
но не завершение прерванной подготовки дайджеста.

## Первые действия

1. В Shell остановить текущий сбор с помощью Ctrl+C. Не запускать параллельные
   повторные сборы. Файловая блокировка обычно предотвращает одновременный
   `preview`, но не заменяет диагностику процесса и потребления памяти.
2. В Render открыть сервис → Events и проверить состояние последнего запуска.
   Затем в Metrics посмотреть Memory за время инцидента.
3. Проверить `/health`: ожидается HTTP 200 и `{"status":"ok"}`.
4. Сохранить диск `/var/data` и переменные Environment. Удаление базы или
   повторный ввод паролей не устраняют нехватку оперативной памяти.

## Что изменено в исправлении

- Архив JSON читается и записывается по частям. Старый формат с полной копией
  предыдущей версии также поддерживается.
- Полностью одинаковые текущие и предыдущие записи сохраняются один раз;
  известное прежнее время перенесённых событий остаётся в истории.
- Для отбора разбирается одна серия событий за раз. История хранит компактные
  даты; кеш всех прошлых повторений отключён.
- CalDAV-объекты и ссылки на XML-ответ предыдущего календаря освобождаются
  перед чтением следующего. Устранена ненужная сериализация XML для подавленного
  debug-журнала.
- В Shell сразу видны этапы чтения, сравнения, отбора и сохранения. Они не
  содержат логинов, названий событий или персональных ссылок.

Полные серии продолжают читаться: ограничение запросов только завтрашним днём
могло бы потерять события, перенесённые с этого дня на другую дату.
Один большой ответ CalDAV всё ещё загружается целиком; поэтому измерение
памяти на конкретном экземпляре Render остаётся необходимым.

## Установка исправления

1. Применить подготовленный pull request в GitHub к ветке `main`.
2. В Render открыть сервис → Manual Deploy → Deploy latest commit.
   В конфигурации автоматическое развёртывание коммитов отключено.
3. Дождаться Live, проверить `/health`, затем заново открыть Shell.
4. Выполнить один запуск:

   ```sh
   .venv/bin/calendar-digest preview --date 2026-10-15 --directory /var/data
   ```

   Дата приведена для текущей проверки. Для следующего дня по Москве можно
   убрать `--date 2026-10-15`. После исправления сразу появится сообщение
   «Читаем сохранённое состояние», затем следующие этапы и итоговый JSON.

5. Во время этого запуска проверить Memory в Render Metrics. Успех — итоговый
   JSON, отсутствие нового перезапуска и сохранение доступности `/health`.
6. Только после успешного полного сбора выпускать новые ссылки `issue-actions`
   и продолжать проверку тестового события.

Если перезапуск повторился, сохранить время и значения Memory, остановить
повторные запуски и продолжить диагностику. Увеличение памяти можно рассмотреть
отдельно после проверки стоимости в Render. Изменение тарифа этим исправлением
не выполняется.

## Воспроизводимая проверка памяти для разработчика

Проверка исправления в двух отдельных процессах на одном сохранённом архиве
с полной предыдущей версией показала снижение пика RSS с **544,91 MiB до
219,44 MiB**. Контрольные суммы сформированных событий совпали. Чистая установка
с закреплёнными зависимостями и 172 автоматические проверки прошли.
Это показатели локального воспроизведения, а не измерения из Render Metrics.

```sh
.venv/bin/python scripts/profile_preview_memory.py PATH_TO_PRIVATE_SNAPSHOT \
  --day 2026-10-15 --source-root PATH_TO_SOURCE_ROOT
```

Скрипт подставляет ответы CalDAV из сохранённого снимка, использует вымышленные
доступы и блокирует сетевые соединения. Временные файлы имеют приватные права
и удаляются. Он выводит только счётчики, время, память и контрольную сумму
результата. Для сравнения нужны отдельные процессы для старой и новой версий.

Это локальное воспроизведение, а не замер живого Render: подставной сервер
удерживает дополнительный архив в том же процессе, веб-процесс в замер не входит,
а задержки и точный формат ответов провайдеров не воспроизводятся. Итоговая
проверка выполняется на Render после обновления. Снимок с личными событиями
не публикуется в GitHub и не передаётся в чат.
