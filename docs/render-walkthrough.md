# Самостоятельное размещение на Render

Эта инструкция размещает сервер кнопок календарного дайджеста. После запуска
он получает постоянный HTTPS-адрес. Автоматическая отправка письма каждый день
в 17:00 по Москве описана отдельно в [email-delivery.md](email-delivery.md).
На действующем сервисе она уже настроена: проверочное письмо получено и одобрено,
расписание включено 15 октября 2026 года, проверена свежая отметка работы
планировщика. Получение первой отправки по расписанию ещё не подтверждено.

Можно выполнить все шаги самостоятельно либо идти по одному шагу вместе
с помощником. Для продолжения в чате достаточно названия экрана или статуса.

Текущий сервис уже размещён: проверены четыре аккаунта, полный дайджест
на 15 октября содержит 35 событий из 11 календарей. После исправления памяти
пользователь проверил перенос личного тестового события Mail.ru с 15:00
на 16:00, затем отмену с удалением из календаря и сохранением в истории дайджеста
без кнопок. Во втором аккаунте Mail.ru проверено принятие приглашения:
ответ виден организатору в первом аккаунте. Другие действия всех провайдеров
этим не проверены. Шаги первого размещения ниже остаются справочными.

## 1. Отдельное окно: регистрация

Откройте обычный браузер на своём компьютере, вне интерфейса чата.
Создайте новое окно: **Ctrl+N** в Windows/Linux или **⌘+N** на Mac.
Введите в адресной строке `https://dashboard.render.com/`.
Помощник не может открыть это внешнее окно из облачной среды.

1. Нажмите **Get Started / Sign Up**, если аккаунта ещё нет, либо войдите.
2. Можно выбрать вход через **GitHub**. Проверьте, что входите под владельцем
   репозитория `pavelbrusser-cmd/-`.
3. Если предложен выбор тарифа рабочего пространства, достаточно **Hobby**.
   Бесплатное рабочее пространство позволяет оплачивать отдельный сервер;
   подписка **Pro** для этой конфигурации не требуется.
4. Остановитесь на главной странице Dashboard. На этом шаге сервис ещё
   создавать не нужно.

Пароли, одноразовые коды и платёжные сведения вводите только на официальных
страницах соответствующего сервиса в этом внешнем окне. Данные, введённые
на Render, обрабатывает Render; отдельное окно само по себе не делает их
недоступными хостингу. Не отправляйте значения, снимки заполненных форм
или ссылки с токенами в чат.

**Результат:** открыт Dashboard Render. Для совместного прохождения можно
написать в чат: «Шаг 1 готов — вижу Dashboard».

## 2. Загрузка подготовленного проекта в GitHub

При первом размещении репозиторий `pavelbrusser-cmd/-` был пустым и публичным.
Исходники уже загружены; повторно выполнять первоначальную загрузку для текущего
сервиса не требуется. Для первого размещения подготовлен отдельный архив
`dist/calendar-digest-render.zip`: код, проверки, конфигурация размещения
и эта инструкция. В нём нет выгрузок календарей, образцов писем, паролей,
локальной базы, адреса получателя или диагностической истории аккаунтов.

1. Сохраните архив из рабочей области на свой компьютер и распакуйте его.
2. Во внешнем окне откройте `https://github.com/pavelbrusser-cmd/-`.
3. В пустом репозитории нажмите **uploading an existing file**. Если в нём
   уже появились файлы, используется **Add file → Upload files**; не заменяйте
   чужие изменения без проверки.
4. Перетащите **содержимое распакованной папки**: файлы и папки `src`, `tests`,
   `scripts`, `docs`. Сам ZIP загружать не нужно. Не переносите внешнюю папку
   целиком как ещё один уровень вложенности.
5. В поле сообщения напишите `Add calendar digest service` и нажмите
   **Commit changes**. Для пустого репозитория используйте ветку `main`.
6. Откройте главную страницу репозитория: в ветке `main` должны быть видны
   `render.yaml`, `pyproject.toml`, `requirements.lock`, `README.md`,
   `src/`, `tests/`, `scripts/`, `docs/`.

Скрытый файл `.gitignore` желательно также включить в загрузку. Если файловый
менеджер его не показывает, для первого запуска Render это не препятствие;
добавьте его позднее перед работой с локальными данными.

Архив содержит только необходимые для размещения файлы. Исходная рабочая
копия с историей разработки остаётся в облачной среде. Сборка архива из неё:
`python3 scripts/package_render.py`.

**Результат:** `render.yaml` открывается непосредственно в корне ветки `main`.

## 3. Подключение Blueprint

1. Вернитесь в Render Dashboard и выберите **New → Blueprint**.
2. Подключите GitHub, если Render предложит это сделать. При выборе доступа
   к репозиториям достаточно **Only select repositories → pavelbrusser-cmd/-**.
3. Нажмите **Connect** напротив этого репозитория.
4. Имя Blueprint: `calendar-digest`. Ветка: **main**.
   Если есть поле **Blueprint Path**, оставьте `render.yaml`.
5. Render прочитает конфигурацию и покажет сервис `calendar-digest-actions`.

Если репозитория нет в списке, откройте настройки подключения GitHub в Render
и разрешите приложению Render доступ к этому репозиторию. Настройки установки
также доступны через `https://github.com/apps/render/installations/new`.

**Результат:** отображается конфигурация сервиса и поля переменных окружения.

## 4. Отдельное окно: доступ к календарям

Заполните следующие поля непосредственно в Render. Из этой облачной среды
их значения автоматически не переносятся.

| Поле Render | Что ввести только в Render |
| --- | --- |
| `ICLOUD_USERNAME` | Адрес Apple Account владельца календарей |
| `ICLOUD_APP_PASSWORD` | Пароль приложения Apple для этого сервиса |
| `MAILRU_1_USERNAME` | Полный адрес первого аккаунта Mail.ru |
| `MAILRU_1_APP_PASSWORD` | Его пароль приложения с доступом к Календарю |
| `MAILRU_2_USERNAME` | Полный адрес второго аккаунта Mail.ru |
| `MAILRU_2_APP_PASSWORD` | Его пароль приложения с доступом к Календарю |
| `MAILRU_3_USERNAME` | Полный адрес третьего аккаунта Mail.ru |
| `MAILRU_3_APP_PASSWORD` | Его пароль приложения с доступом к Календарю |

Сохраните прежний порядок трёх аккаунтов. Основные пароли Apple и Mail.ru
в эти поля не вводятся: нужны именно пароли приложений.

Если сохранённых паролей приложений у вас нет, создайте отдельные для Render:

- Apple: `https://account.apple.com/` → «Вход и безопасность» →
  «Пароли приложений» → новый пароль с названием `Calendar Digest Render`.
- Каждый аккаунт Mail.ru: `https://account.mail.ru/user/2-step-auth/passwords/`
  → создать пароль → **«Полный доступ к Календарю»**.

Создание нового пароля не требует отзыва паролей, которыми пользуется
облачная среда разработки. Скопируйте новые значения из интерфейса провайдера
в Render и сохраните в своём менеджере паролей.

`DIGEST_ACTION_SECRET` и `DIGEST_WEB_PASSWORD` Render создаёт автоматически.
Их не нужно придумывать или отправлять в чат. Остальные технические переменные
также заданы в `render.yaml`.

**Результат:** восемь полей календарей заполнены. В чат достаточно «Доступы введены».

## 5. Отдельное окно: проверка стоимости и оплата

Перед созданием проверьте состав заказа:

| Настройка | Значение |
| --- | --- |
| Рабочее пространство | Hobby достаточно |
| Сервис | Один Python Web Service |
| Сервер | `0.5c-512mb`: 0,5 CPU, 512 MB RAM |
| Регион | Frankfurt |
| Постоянный диск | 1 GB, путь `/var/data` |
| Дополнительные сервисы | База Postgres и отдельный Cron не требуются |

По опубликованному прайсу, проверенному 14 октября 2026 года, ориентир —
**$7 в месяц за сервер + $0,25 за диск 1 GB**, всего **$7,25 в месяц**
без налогов и дополнительных расходов по использованию. Окончательные условия
проверьте на экране Render перед созданием сервиса. Бесплатный сервер
не подходит: здесь нужны постоянный диск и работа без засыпания.

Если Render запросит способ оплаты, заполните его в официальном платёжном
интерфейсе Render или платёжной форме, открытой самим Render. Карта, CVC,
платёжный адрес и код подтверждения банка остаются в этом внешнем окне.
В чат их вводить не нужно. Порядок появления формы зависит от состояния
аккаунта: до или во время создания сервиса.

Проверив настройки и стоимость, нажмите **Deploy Blueprint**.
Это создаёт платные ресурсы. Простое закрытие окна впоследствии не останавливает
оплату созданного сервиса.

**Результат:** Render начал сборку и развёртывание.

## 6. Проверка публичного адреса

1. Откройте созданный сервис `calendar-digest-actions`.
2. В разделе **Events / Logs** дождитесь успешного развёртывания, обычно
   обозначенного **Live**. Сборка устанавливает зависимости и выполняет
   автоматические проверки; реальные события при сборке не изменяются.
3. Откройте HTTPS-адрес `https://…onrender.com`, указанный вверху страницы сервиса.
   Название зависит от доступности адреса; собственный домен не требуется.
4. Главная страница должна сообщать о готовности сервиса. Добавьте к адресу
   `/health`: ожидаемый ответ — `{"status":"ok"}`.
5. В **Environment** найдите созданный `DIGEST_WEB_PASSWORD` и сохраните его
   в своём менеджере паролей. Он нужен владельцу для страницы действия,
   открываемой из письма. Главная страница сама по себе не содержит список событий.
6. Проверьте в настройках диска: размер 1 GB и путь `/var/data`.

Успешный `/health` подтверждает запуск веб-сервиса. Подключение к календарям
проверяется следующим шагом.

## 7. Проверка чтения четырёх аккаунтов

В панели **этого же сервиса Render** откройте **Shell**. Выполните по очереди:

```sh
.venv/bin/calendar-digest probe-icloud --days 1
.venv/bin/calendar-digest probe-mailru --account 1 --days 1
.venv/bin/calendar-digest probe-mailru --account 2 --days 1
.venv/bin/calendar-digest probe-mailru --account 3 --days 1
```

Команды читают календарь на следующий день по Москве и печатают счётчики.
Они не изменяют события и не отправляют письма. Пустая выборка допустима,
если на этот день нет событий; сообщение об ошибке подключения — отдельный случай.
Полные результаты в чат переносить не требуется.

Для проверки формирования дайджеста выполните:

```sh
.venv/bin/calendar-digest preview
```

Дата вычисляется как завтра по Москве. Приватные файлы сохраняются
в `/var/data`; это не общедоступная папка сайта. Первая загрузка всех календарей
может занять несколько минут. Письмо при этом не отправляется.

**Результат:** публичный сервер запущен, четыре проверки чтения завершились
без ошибок, предпросмотр сформирован.

## 8. Что сообщить для продолжения

Достаточно написать: «Render Live, четыре аккаунта проверены». Можно прислать
базовый адрес `https://…onrender.com` без `/a/…`, параметров и токенов.
Он понадобится для следующей проверки. Пароли и результаты с личными событиями
не нужны.

Перенос личного тестового события первого аккаунта Mail.ru уже проверен.
Отмена этого события через удаление с приватным архивом также проверена
на действующем сервисе; правила и границы описаны в [cancellation.md](cancellation.md).
Проверка принятия приглашения вторым аккаунтом Mail.ru подтвердила ответ
у организатора в первом аккаунте. Отмена экземпляра серии требует отдельной
проверки на тестовой серии.

Для нового размещения следующий шаг — настройка SMTP-отправки и её проверка
по [email-delivery.md](email-delivery.md). На действующем сервисе это уже
выполнено и ежедневное расписание включено. Одна только публикация нового
веб-сервиса расписание не запускает. Подключение push на iPhone описано
в [push-notifications.md](push-notifications.md).

## Если что-то не получилось

| Ситуация | Что проверить |
| --- | --- |
| Render не находит `render.yaml` | Файл лежит в корне ветки `main`, не внутри ZIP или внешней папки |
| Не найден `scripts/setup.sh` | При загрузке в GitHub сохранилась структура папок |
| GitHub-репозиторий отсутствует в Render | Доступ приложения Render к нужному репозиторию |
| Сборка завершилась ошибкой | Сообщите название этапа и обезличенный текст ошибки; значения Environment не копируйте |
| Ошибка входа в календарь | Полный адрес, правильный аккаунт и пароль приложения, сохранённые в Render |
| Публичная страница работает, а письмо не приходит | Проверить `delivery-status`, свежесть отметки планировщика и почтовую папку «Спам»; для нового размещения сначала настроить SMTP и включить расписание по инструкции |
| При открытии действия показано «Календари временно заняты» | Дождитесь завершения сбора и повторите попытку; ссылка не израсходована |

Автоматический деплой новых коммитов отключён в конфигурации. Отдельная настройка
**Blueprint Auto Sync** управляет применением изменений `render.yaml`;
для ручного управления её также можно выключить в настройках Blueprint.
При обновлении кода запускайте **Manual Deploy → Deploy latest commit**
в панели сервиса. Не меняйте ключ подписи и не удаляйте диск при обычном обновлении:
они нужны для действующих ссылок и сохранённого состояния.

Для первого подключения ежедневной отправки явно задайте в настройках сервиса
**Start Command**: `.venv/bin/python scripts/start_service.py`.
Ручной деплой не гарантирует применения изменённого `startCommand` из Blueprint.
При первом подключении сохраните `DIGEST_SCHEDULE_ENABLED=false`; включение
выполняется после проверки настоящего письма и итогового подтверждения
владельца. На действующем сервисе этот этап завершён: при обычном обновлении
кода сохраняйте уже одобренное значение `true`.

[GitHub](https://render.com/docs/github),
[поля секретов](https://render.com/docs/blueprint-spec#prompting-for-secret-values),
[постоянные диски](https://render.com/docs/disks),
